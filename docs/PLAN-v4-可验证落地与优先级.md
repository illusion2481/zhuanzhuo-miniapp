> 定位：这是 **PLAN-v3（商业化/留存/平台化长期规划）之前的一张「把系统真正跑通、能 demo、商家可运营」的落地执行清单**。
> 执行前提：代码层验证已全绿（typecheck / lint / seed:check / `npm run test:cloud` 13 pass）；本 Plan 聚焦「云环境端到端可验证 + 真实业务缺口」，分 **A → B → C** 三个 Sprint，**A 先做**。

## 0. 现状核查结论（基于源码核实的三个判断）

> 以下三条已通过 grep 源码逐条印证，不是猜的。

### ① 预约流程「跑不通」—— 但不是流程缺，是云端初始化没做完

- **座位数据是有的**：`cloudfunctions/seedData/seedPayload.js` 内置 3 个自习室、26 个座位（A-1 ~ C-6），含 `type:'room'` 的 categories 文档 + `metadata.seats` 座位平面。
- 但这些数据**存在云数据库里、由 `seedData` 云函数注入**；前端 `services/room.ts#listRooms` 虽然有 catch 兜底，但兜底走的 `listRoomSummaries()` 仍是**从 categories 集合（经 categoryList 云函数）取**，不是本地硬编码。
- 结论：**云端没部署 13 个云函数 / 没跑 seedData 时，房间页为空 → 预约走不下去**。这不是流程缺失。
- ✅ 解法：按 `docs/云部署与端到端验证清单.md` 顺序完成部署后，模拟器即可完整验证「选房 → 选座 → 选时段 → 预约 → 签到」。
- （可选增强，Sprint A 含）给前端 `room.ts` 加一份**纯前端内置演示兜底**（3 房 26 座常量），云端未就绪时也能点通 UI —— 详见 Sprint A-3。

### ② 「死登录」的真实情况 —— 是静默 openid 登录，非伪造，但没有感知

- 登录用的是 **openid 静默登录**：`cloudfunctions/login/index.js#L57-58` 取 `cloud.getWXContext().OPENID`（微信平台发放的真实身份标识，每用户每小程序唯一，无需密码）。
- `app.ts onLaunch` 启动时**自动调用 `login()`**，所以用户一进小程序就是「已登录」态，角色默认 `student`。
- 结论：**它不是假登录**，只是没有可见的登录动作、也没有手机号/资料授权。
- 手机号登录需要**认证企业小程序资质**，属后续可选（Sprint C-3 会先说明再动）。

### ③ 商家后台 —— 只有聚合统计，没有可处理的明细（真实缺口）

- 现状：admin 端只有 `adminStats`（四宫格 + 状态分布），来自 `services/statistics.ts#fetchAdminStats`；`pages/admin/admin.ts` 仅有状态标签映射（pending→待签到 / cancelled→已取消 / no_show→爽约 等），**没有任何逐条预约列表、没有任何处理动作**（代取消 / 核销 / 标记爽约 / 导出）。
- 结论：**「商家能逐条处理预约」是当前最大业务缺口**，在 Sprint B 补齐。

## 二、执行计划（A → B → C）

### 🔷 Sprint A —— 功能可验证（先做，让系统"能演示"）

**目标**：你能亲眼看到预约全流程跑通。

| # | 任务 | 说明 | 产出/验收 |
|---|---|---|---|
| A-1 | 云部署全流程 | 建 3 集合（users/records/categories）→ 传 13 云函数 → 跑 `seedData` → build npm | 房间页有 3 房 26 座，非空 |
| A-2 | 模拟器完整跑通 | 「选房→选座→选时段→预约→签到」回填验证 | 走查报告登记 PASS/FAIL |
| A-3 | **前端演示兜底** | 在 `services/room.ts` 内置 `DEMO_ROOMS`（3 房 26 位常量），`roomList` 失败时返回本地数据 | 云端未就绪也能点通 UI |

> A-3 设计要点：复用现有 `RoomSummary` / `SeatDef` 类型；兜底数据与 `seedPayload.js` 一致；仅作「无云端兜底」，上线时可保留（不影响真数据，因 `res.data.length` 有真值时不走兜底）。

### 🔷 Sprint B —— 商家后台（核心缺口）

**目标**：商家能逐条处理预约信息。

| # | 任务 | 说明 | 验收 |
|---|---|---|---|
| B-1 | **新云函数 `adminRecords`** | 按日期 / 状态 / 房间 / 座位筛选 + 分页拉预约明细；**复用 `ADMIN_OPENID_HASHES` 鉴权**（对齐 login/adminStats） | 非 admin 返回 403，admin 可分页 |
| B-2 | **admin 页升级：预约明细列表** | 复用 `services/record.ts` 类型，展示预约列表（含筛选/分页） | 能按条件筛选 |
| B-3 | **列表操作** | 代客取消 / 手动核销签到 / 标记爽约 / 结束使用 | 状态能正确流转 |
| B-4 | **CSV 导出** | 导出当日预约名单 | 生成 .csv 可下载 |
| B-5 | **预留爽约黑名单** | 爽约 N 次后禁止预约（本期只做结构预留 + 常量配置，不强制） | 常量存在、文档说明 |

### 5️⃣ Sprint C —— 登录体验

| # | 任务 | 说明 | 验收 |
|---|---|---|---|
| C-1 | 去掉启动静默登录 | 首次进「我的」显示未登录 + 显式「微信登录」按钮 | 未登录态可感知 |
| C-2 | 接入头像昵称填写组件 | 2022 后 `getUserProfile` 只返回默认昵称，需资料填写组件 | 能录入昵称/头像 |
| C-3 | （可选）手机号登录 | 需认证企业小程序资质；**先说明资质要求再动** | 说明清楚后再决定 |

## 三、建议执行顺序

```
Sprint A（能演示，1 天）
   └─ Sprint B（商家刚需，2-3 天）
        └─ Sprint C（体验，1 天）
```

> 理由：A 让系统「能跑」，是后续一切验证的前提；B 补的是**真实到店运营的硬伤**（现在商家连预约名单都看不到）；C 是体验打磨，优先级最后，且 C-3 涉及资质申请，需你确认。
