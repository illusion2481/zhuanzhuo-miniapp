# 专注座 · 功能优化方案（对标成熟自习室预约产品）

> 生成时间：2026-09-18
> 输入：`系统功能与逻辑链路报告-2026-09-18.md` + 项目现状核查 + 5 个已上线同类产品案例对标
> 目标：在现有高完成度预约闭环之上，补齐"能运营、能增长、能变现"的能力短板

---

## 0. 基线判断（现状速览）

**已具备（差异化优势，必须保留并深化）**
- 完整预约闭环：房间/座位 → 下单（事务冲突校验 + 开放时段"夹"）→ 签到（签到码/座位码/无凭证三凭证）→ 暂离/返回 → 超时违约（定时器 + 登录惰性双保险）→ 取消/改约。
- AI 选座 + 学习计划 + 番茄钟 + 学习排行 + AI 学习总结。
- 管理后台：自绘趋势/高峰/占用率图表、座位维护、信用管理。
- 订阅消息：4 张模板 + 前端授权/云端发送分离。
- 工程质量高（TS/入参白名单/幂等/268 项测试）。

**明显短板（成熟产品的标配，本系统缺失）**
| 维度 | 缺口 |
|---|---|
| 实时性 | 座位占用靠前端 15s 轮询，无实时推送 |
| 增长 | 无行为埋点（UV/PV/转化漏斗）、无分享裂变（海报/邀请/拼座）、无地图导航 |
| 留存 | 无连续签到天数、无长期学习习惯看板、无评价评分 |
| 商业化 | 无会员/积分/次卡/优惠券/支付 |
| 体验 | rooms 页无搜索/筛选/排序、无客服入口、无续时快捷入口 |
| 消息 | 无订阅发送历史归档、无站内信/消息中心 |

## 1. 对标：成熟产品都验证了什么（共性能力矩阵）

从检索到的已上线案例（飞傲软件付费自习室方案、3 所高校稳定运行 8 个月的小程序、共享无人自习室方案、全栈架构实践）提炼出 9 项共性能力：

1. **实时座位同步（延迟 150–300ms）**：普遍用 WebSocket 或云开发实时推送，而非轮询。某高校案例强调"实时同步延迟控制在 300ms 以内"是核心体验。
2. **支付与卡券核销**：下单支付、月卡/次卡/小时卡后台核销、优惠券——这是付费自习室的商业化底座。
3. **无人化管控**：扫码门禁/动态二维码核销、环境控制（灯光/空调）。
4. **精准选座 + 筛选**：按区域（静音区/讨论区/窗边）、设施（插座/台灯/储物柜）筛选，所见即所得。
5. **运营看板**：高峰时段预测、使用率热力图、异常预约监控（恶意占座识别）、黑名单系统（3 次违约自动禁用 7 天）。
6. **智能续时 + 暂离锁定**：结束前提醒并一键延长（座位未被他人预约前提下）。
7. **发现页/多门店**：附近门店、按区域/评分/价格筛选、门店详情（环境图/设施/计价）。
8. **评价评分**：座位/门店评分 + 标签，反向 feed 选座推荐。
9. **性能与分包**：座位地图独立分包、虚拟列表应对 500+ 座位。

> 结论：成熟产品不是"多了几个按钮"，而是把**实时性、运营数据、商业化、评价闭环**做成了基础设施。本系统恰好在这四块缺位。

## 3. 优化方案（分三期，优先级驱动）

### 🟥 P0 — 体验地基与转化（建议 1–2 周，ROI 最高）

**P0-1 实时座位同步：用云开发 `watch` 替换 15s 轮询**
- 对标：高校案例"实时同步 <300ms"是核心体验；云开发实时推送延迟约 150ms、按量计费。
- 现状：`seats.ts` 每 15s `setInterval` 拉占用，弱网下"图绿点却报已约"。
- 方案：在 `seats.onLoad` 对 `records` 集合（按房间/日期过滤）建立 `db.watch()` 长连接，云数据库变更主动推前端；保留手动下拉刷新 + 失败回退轮询作为兜底（复用现有三级降级思路）。
- 落地要点：注意 watch 在小程序后台/锁屏会断开，需 `onHide` 暂停、`onShow` 重建；`expireRecords` 翻状态后 watch 自动推，无需前端再轮询。
- 收益：座位状态延迟从 15s → <300ms；同时**减少约 90% 的无谓请求**，降云函数调用成本。

**P0-2 rooms 页搜索 / 筛选 / 排序**
- 对标：所有成熟产品都把"按区域/设施筛选 + 排序"作为选座标配。
- 现状：`rooms.ts` 仅列表 + 迷你密度图，无筛选无排序；`seats.ts` 已有 `window/power/outlet/quiet` 特征高亮可借鉴。
- 方案：rooms 页顶部加筛选栏（靠窗/电源/静音/维护态）、关键词搜索（房间名）、按"空闲率 / 距离打烊时长"排序；筛选条件透传到 seats 页预筛。
- 收益：用户找座时间显著下降（成熟案例核心指标"从打开到预约 ≤15s"）。

**P0-3 一键续时（替代繁琐改约）**
- 对标：智能续时是成熟产品提升座位周转率的标配。
- 现状：只有 `updateReservation` 改约，需重选时段。
- 方案：使用中记录（`active`）结束前 15min 弹提醒 + 卡片"延长 30/60min"按钮；调用 `updateReservation` 重校验冲突（座位未被他人预约才放行），复用现有开放时段"夹"逻辑。
- 收益：减少"到点被迫离开/重新抢座"的流失，提升单座日周转。

**P0-4 客服入口**
- 对标：任何面向用户的服务小程序都需客服会话。
- 方案：在 `profile` 页加 `contact-button`（或通过 `openCustomerServiceChat`）；`adminOps` 可加"拉黑/回复"轻量后台。
- 收益：承接违约申诉、签到码异常、退款咨询，降低差评。

**P0-5 埋点地基（转化漏斗 + 留存）**
- 对标：没有埋点就无法做后续所有增长动作（这是成熟团队的第一块地基）。
- 方案：用 `wx.reportAnalytics`（小程序后台配置自定义事件）埋关键节点：`room_view / seat_tap / booking_confirm / checkin_done / study_start / share_send`；在 `store` 或云函数侧按 `open_id_hash` 聚合次日/7 日留存。
- 收益：拿到预约转化率、签到率、学习启动率，为 P1 看板与决策提供数据。

### 🟧 P1 — 增长与留存（建议 2–4 周）

**P1-1 运营看板升级（在现有 adminStats 之上）**
- 对标：高峰预测、使用率热力图、异常监控是运营标配。
- 方案：admin 看板加①预约转化漏斗（浏览→预约→签到）②座位利用率热力图（按小时×房间）③异常预约监控（短时间内高频预约/签到后立即离开的可疑行为标记）。
- 复用：现有 `adminStats` 聚合 + 自绘 CSS 图表（无需引入图表库，控制主包体积）。

**P1-2 连续签到 / 打卡天数 + 长期学习习惯看板**
- 对标：streak 是学习类产品的留存引擎。
- 方案：新增 `users.streak` / `users.last_checkin_date`，签到时递增/断签重置；`study` 页或 `profile` 展示连续天数、周/月专注趋势（复用 `studyRecord.summary` + `aiSummary`）。

**P1-3 评价评分系统（反向 feed AI 选座）**
- 对标：评分 + 标签是选座推荐的反馈闭环。
- 方案：完成使用后对"座位/自习室"打分（安静度/舒适度/插座可用性）+ 标签；写入新集合 `reviews`；`aiRecommend` 在打分阶段把历史评分作为权重因子（强化现有 AI 能力，形成差异化）。

**P1-4 分享裂变（海报 + 邀请 + 拼座）**
- 对标：分享海报/邀请是自习室低成本获客手段。
- 方案：基于现有 `utils/share.ts`（`buildShare` 已定义未接），加①分享海报（canvas 生成带小程序码图片，落到云存储）②邀请好友得"信用保护/优先推荐"③可选"拼座"（同行人共约相邻座位）。

**P1-5 消息中心（订阅发送历史 + 站内信）**
- 对标：订阅消息无归档，用户"收没收到"不可查。
- 方案：新增 `notify_logs` 集合，`notify` 云函数每次发送落库；`profile` 或独立"消息"页展示历史；补"系统通知/活动"站内信能力。

### 🟩 P2 — 商业化与规模化（建议 4–8 周，受资质/硬件约束）

**P2-1 会员 / 次卡 / 优惠券 / 支付**
- 对标：月卡/次卡核销是付费自习室营收核心。
- ⚠️ 约束：**微信支付需企业主体 + 商户号**，个人主体小程序无法接入；落地前需确认主体资质。
- 方案：订单模型引入 `order`/`membership` 集合；`createReservation` 支持"卡券核销"或"微信支付"两种结算；`adminOps` 支持发卡/发券/退款。

**P2-2 发现页 / 多门店**
- 对标：附近门店 + 区域/评分/价格筛选是连锁扩张的基础。
- 适用条件：仅当有多门店/多校区规划时启动（当前 `categories` 是单校区多房间模型，需先引入 `study_room` 门店维度 + 经纬度 + 地址）。
- 方案：新增门店维度、`wx.getLocation` + `<map>` 导航到店（当前全仓 0 命中地图能力）。

**P2-3 异常监控 / 恶意占座 + 黑名单自动化**
- 对标：3 次违约自动禁用 7 天；异常预约监控识别恶意占座。
- 方案：在现有违约梯度（30min/2h/24h）之上，于 `expireRecords` 增加"短时高频预约"识别，自动升级 `banned_until`；admin 看板异常 Tab 可视化。

**P2-4 分包加载**
- 对标：座位地图分包可省主包 1.2MB+。
- 方案：将 `seats`（含 SeatMap 组件）拆为独立分包；进一步压主包、给 P2 商业化留体积空间（延续本次已做的 TDesign 裁剪成果）。

**P2-5 门禁 / 扫码核销联动（硬件，可选）**
- 对标：扫码门禁是无人化运营关键。
- 方案：预约成功生成动态二维码，对接门禁控制器；非必选，取决于是否上硬件。

## 4. 优先级与排期建议

| 阶段 | 周期 | 关键交付 | 为什么先做 |
|---|---|---|---|
| **P0** | 1–2 周 | 实时 watch、rooms 筛选、续时、客服、埋点 | 不动商业化资质，纯前端+云函数即可上线，直接提升核心体验与数据地基 |
| **P1** | 2–4 周 | 看板升级、连续签到、评价、分享、消息中心 | 基于 P0 埋点数据做增长与留存，强化 AI 差异化 |
| **P2** | 4–8 周 | 会员支付、多门店、黑名单自动化、分包、门禁 | 依赖主体资质/硬件决策，规模化阶段再做 |

**先做 P0 的理由**：P0 五项全部不依赖外部资质，且实时性（watch）、筛选、续时都是"用户一用就感知"的体验提升；埋点是后续所有增长动作的先决条件。这与成熟案例"先解决实时同步与极简预约，再上运营与商业化"的演进路径一致。

## 5. 风险与注意事项（结合本系统脆弱点）

1. **五处跨端一致性（报告 §4）仍是雷区**：引入续时/改约/筛选时，凡涉及超时 15/30min、开放时段"夹"、订阅模板 ID、事务返回值，必须同步 `config/constants.ts`、`expireRecords`、`createReservation`、`roomList`、`bookingWindow.ts` 等多处——改动后用 `cloud-logic.test.cjs`（268 项）与 `booking-window.parity.cjs`（15 项）回归。
2. **watch 实时监听的断开重建**：小程序 `onHide` 会断连，务必在 `onShow` 重建并在 `onUnload` 关闭，避免泄漏长连接。
3. **主包体积红线（2MB，80051 报错）**：P2 分包前勿在主包塞大图/图表库；评价图片、分享海报走云存储，不进包。
4. **埋点合规**：`wx.reportAnalytics` 需在微信公众平台"自定义分析"配置事件；涉及用户行为数据注意隐私告知。
5. **支付主体约束**：P2-1 商业化前先确认小程序主体为企业且已开通微信支付，否则整块设计需暂缓。
6. **评价/分享内容安全**：评价文本、分享文案走 `msgSecCheck`（现有 UGC 护栏已覆盖 `goal`，扩到 `reviews` 即可）。

## 6. 一句话总结

> 专注座现在是一座"功能扎实但缺运营心脏"的 MVP。先用地云开发 `watch` 把实时性补齐、用埋点把数据地基打牢（P0），再用评价与分享把 AI 选座的飞轮转起来、把留存做厚（P1），最后在确认主体资质后上会员支付与多门店（P2）——这条路径与已上线成熟产品的演进高度一致，且每一步都能复用现有工程资产（adminStats、aiRecommend、subscription、测试套件）。
