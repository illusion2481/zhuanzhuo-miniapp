>
> ⚠️ **前置条件（全部满足才开测）**：
> 1. 云函数已 GUI 上传：`notify` / `createReservation` / `updateReservation` / `expireRecords` / `cancelReservation` / `login` / `roomList` / `checkin`
> 2. `expireRecords` 超时已改为 **20 秒**（默认仅 3 秒，扫描+推送会超时失败）

> 5. **前端代码已重新编译并重开真机调试**（或上传体验版）——只改本地文件、手机仍跑旧包，改动一律不生效

> - **`login` 决定违约次数是否可靠**（不传 → 超时了次数也不涨，见「必读 H」）

## 必读 A · 真机完全不弹授权卡？按概率逐条排除

1. **前端代码没更新**（最常见）：改完必须**重新编译 + 重开真机调试**（或上传体验版）。手机跑的还是旧包 → 依然不弹。
2. **下单入口走错**：真正下单入口是**座位图底部抽屉**的「立即预约」（`pages/seats` → `onConfirmBooking`），**不是** `pages/reservation`。两个入口都必须接订阅授权；先确认你点的是哪一个。
3. **批量模板「全有或全无」**：一次请求 3 张模板时，**只要其中任意一张 ID 无效（未选用 / 不属本账号 / 已过期 / 已封禁），整批会被微信拒绝，一张卡都弹不出来**，且报错只落在 fail 回调里，极易被忽略。
   - ⛔ **不要再用「批量失败 → 自动重试第一张」的兜底**（2026-09-17 已删除）：第二次调用必然发生在 `await` 之后，点击手势已经用掉，微信**必定**报 `can only be invoked by user TAP gesture`；更糟的是这条「调用时机不对」会**覆盖真实失败原因**，让人彻底查不出问题。
   - ✅ 现在的做法：批量失败时**如实上报原因**；用户想重试就**再点一次**「开启预约通知 → 开启」（新的一次点击 = 新的手势）。若失败原因是 20002 / 20004，失败弹窗会直接给「去设置」按钮。
4. **用户拒过 / 关掉了总开关**：
   - `20002` = 之前拒过。**只要当时没勾「总是保持以上选择」，再点一次「开启」仍会正常弹卡** —— 这就是正常的重试路径，不要以为被拒一次就废了。
   - `20004` = 关闭了「接收订阅消息」总开关 → 需点小程序右上角「…」→ 设置 → 打开。
5. **⚠️ 被「总是保持以上选择」永久记住（2026-09-17 新增 · 最容易被误判成「按钮点了没反应」）**

   微信授权卡底部有一个 **默认就是勾选状态** 的「总是保持以上选择，不再询问」。用户点「拒绝」时如果没手动取消这个勾，微信会把该模板**永久**记为拒绝：

   - 之后每次调用 `wx.requestSubscribeMessage` **都不再弹卡**，直接返回 `reject`（表现就是"点了没反应"）；
   - 这是微信平台的硬规则，**没有任何 API 能重置**；`wx.openSetting` 也只能开总开关，不能单方面解除模板级的记录；
   - **判定依据**（官方文档明文）：`wx.getSetting({ withSubscriptions: true })` 的 `itemSettings` **只返回勾过「总是保持以上选择」的模板**。所以 `itemSettings[tmplId] === 'reject'` ⇔ "被永久记住了"；反之 `itemSettings` 里查不到该模板 ⇔ 下次仍会正常弹卡。`utils/subscribeSetting.ts` 就是靠这条区分「用户侧永久拒绝」和「模板侧 ID 无效」。

   **两条恢复路径**
   - **① 用户自助**：小程序右上角「**… → 设置 → 订阅消息**」→ 找到对应模板手动打开。
     ⚠️ 回到小程序后**必须再点一次「开启」**：微信在设置页改动后会把之前累计的订阅次数**清 0**，不重新调用 `requestSubscribeMessage` 就拿不到下发次数（所以代码里只提示"再点一次开启"，不会自动调）。
   - **② 开发者重置（最彻底）**：到公众平台**重新选用一张同内容的模板**（得到全新的 tmplId），替换 `miniprogram/config/subscribe.ts` 里对应的一项。新模板对用户而言是「从未选择过」→ 会重新弹卡。
     ⚠️ 换 ID 后 `SUBSCRIBE_KEYS` 的关键词编号可能不同，需打开模板详情核对（只改那一行）。
6. **模板未审批通过**：公众平台「我的模板」中必须是**已通过**状态；未通过时推送会被拒，授权卡也可能不弹。

**一键诊断入口**：失败弹窗本身（20002 / 20004 会各给一句准确原因 +「去设置」按钮）。
真机排障另可在 **vConsole** 里查看 `[订阅授权] 发起请求` 与 `[订阅授权] 请求失败` 两条日志 —— 能直接看到请求了哪些 tmplId、失败在哪个 errCode。

## 必读 B · 幽灵记录清理（2026-09-16 事务 bug 遗留）

`createReservation` 曾误读 `runTransaction` 的返回值：**记录其实已成功入库，却给你返回「预约失败，请稍后重试」**。后果有两层：

1. 每次「失败」都真的建了一条预约 → **占座**，之后再约同一座位就会提示「该时段座位已被预约」；
2. 这些记录 `status = pending_checkin`，**15 分钟后会被 `expireRecords` 判为爽约**，白扣违约次数；累计到梯度还会**禁约 30 分钟 / 2 小时 / 24 小时**。

**清理步骤**：

> **管理后台怎么进 / 怎么切页**（之前写成「tab 切到用户」太含糊，这里说清）：
> 小程序 →「我的」→ 点「**管理统计（管理员）**」。页面上方有**一排 4 个标签**：
> **看板 ｜ 预约 ｜ 座位 ｜ 用户**。点哪个，下面就换成哪一块内容 —— 这就是所谓「切换到用户」，
> 也就是**点顶部第 4 个标签「用户」**，下面的标题会显示「**用户与信用**」。

1. **先上传修复后的 `createReservation`**（否则边清边冒新幽灵）；
2. 点顶部标签「**预约**」：
   - 日期筛选点「**全部**」（默认是「**今日**」，旧记录会看不见）→ 点「**刷新**」；
   - 逐条核对「开始时间」，找出**你没打算保留**的记录（特征：状态「**待签到**」、时间对不上，尤其是你当时收到「预约失败」的那几个时间点）；
   - 每条点红色按钮「**取消并释放**」→ 座位立即释放。
3. 核对违约是否被虚增：「我的」页看「**爽约 N 次**」；若是被幽灵记录顶上去的，点顶部标签「**用户**」→ 搜索框**留空**点「**搜索**」列出全部 → 找到你自己那行（显示「违规 N 次 · …」）→ 点「**解除禁约并清零**」（只想解禁、保留次数就点「仅解除禁约」）；
4. 之后用修复版本**新约一笔**再验证，**不要**拿旧记录复测。

## 必读 C · 座位图不显示占用、点预约才报「已被预约」

这是**显示口径与写入口径不一致**导致的自相矛盾（2026-09-16 已修）：

- `roomList`（决定座位图颜色）有一层「惰性释放」：`pending_checkin` 开始已过 **15 分钟**、`paused` 最后更新已过 **30 分钟**，就**不再算占用** → 座位显示**绿色空闲**。
- 而 `createReservation`（决定能不能下单）早期**没做**同样的超时过滤 → 它仍看得见这条记录 → 报「该时段座位已被预约」。

⇒ 表现就是：**座位图一片绿，点「立即预约」却被拒**。修复后两者已完全同口径（`releasedByTimeout` 逐字对齐 `isStale`）。

**怎么判断该不该让位？** 看冲突记录的状态：

| 冲突记录状态 | 含义 | 你应该 |
|---|---|---|
| `pending_checkin` 且开始已过 **> 15 分钟** | 人没来，座位本就该释放 | 修复后可直接约上；若仍被拒 → 云端 `createReservation` 还是旧版，重新上传 |
| `active`（使用中） | 椅子上真有人，**永不超时** | 换座位 |
| `pending_checkin` 且开始未到 / 没过 15 分钟 | 别人刚约的 | 换座位或换时段 |
| `paused` 且最后更新已过 **> 30 分钟** | 暂离太久，座位已释放 | 修复后可直接约上 |

> ⚠️ 别被顶部「所选时段空闲 18 / 共 18」误导：那行文字是**页面加载时**的房间快照，失败后不会自动重算。修复版已加「失败即静默重拉」，但仍以**座位格子的颜色**为准。

## 必读 E · 违约倒计时与签到时限（2026-09-16 新增）

占用/释放的时限（`roomList` / `expireRecords` / `createReservation` / `checkin` 四处同口径，改一处要一起改）：

| 状态 | 时限 | 到点后果 |
|---|---|---|
| `pending_checkin` 待签到 | 开始后 **15 分钟**内必须签到 | 判**爽约** + 释放座位，他人可立即预约 |
| `paused` 暂离中 | 最后更新后 **30 分钟**内必须返回 | 判**爽约** + 释放座位 |

现在「我的预约」卡片会**提前把还剩多久摆出来**：

- 琥珀色「⏳ 未签到将在 **12 分钟**后自动释放座位并记爽约」；
- 红色「⏳ …」= 剩余 **≤ 5 分钟**，即将释放；
- 灰色「⛔ 已超过签到时限（开始后 15 分钟），座位已释放，本条将记为爽约」= 已成定局。

配套行为：
- 超过时限后，卡片上的**签到二维码与「手动签到 / 扫码签到」按钮会自动收起**，换一句说明 ——
  因为服务端此时也会拒绝（`CHECKIN_EXPIRED`）。这一步是必须的：若仍放行签到，
  就会出现**同一座位两条 `active` 记录**（你和后来约到该座位的人「一椅两人」）。
- 想让系统在超时前推微信提醒，必须先开「预约通知」（见下一条）。

## 必读 G · 弹「未能开启通知：can only be invoked by user TAP gesture」（2026-09-16 修复）

**完整报错**：
> 订阅授权失败：requestSubscribeMessage:fail can only be invoked by user TAP gesture

**含义**：微信要求 `wx.requestSubscribeMessage` 必须由**用户点击手势同步唤起**，
而调用它的那一刻**已经脱离点击手势**了，所以一张卡都不会弹。

**唯一常见原因**：代码在点击回调里先 `await` 了别的东西（弹窗 / 云调用），
await 一挂起手势就断了。注意 **`await wx.showModal()` 与 `await` 云调用一样会断手势**。

**已修复的四处调用点**（统一改成「点击回调的第一句、同步调用」）：

| 动作 | 入口 | 状态 |
|---|---|---|
| 座位图下单 | `pages/seats` `onConfirmBooking` | ✅（原先就对） |
| 预约页下单 | `pages/reservation` `onSubmit` | ✅（原先就对） |
| 「开启预约通知」 | `pages/profile` `onConfirmEnableNotify` | ✅ 2026-09-16 修：确认层改自绘 |
| 取消 / 结束使用 | `pages/myReservations` `onConfirmCancel` | ✅ 2026-09-16 修：确认层改自绘 |

**你要做的**：**重新编译 + 重开真机调试**（或上传体验版）。
这是纯前端改动，**不需要重传云函数**。

> 📌 本项目的确认框（「是否开启预约通知」「确定要取消这次预约吗」）**必须保持页面自绘**。
> 以后新增任何「先确认、再授权」的入口，都要照此处理，否则又会报这个错。

## 必读 H · 明明超时了，违约次数却不涨 / 卡片一直写「待签到」（2026-09-16 修复）

**现象**：预约开始时间早过了 15 分钟，卡片正文写着「已超过签到时限…将记为爽约」，
徽标却还挂着「待签到」；「我的」页的违约次数也一动不动。

**两个叠加的原因**：

1. **结算根本没发生**：判违约的 `expireRecords` 是**定时触发器**云函数。
   触发器没部署、或函数超时还是默认 3 秒被截断时，它压根不会跑，
   记录就永远停在 `pending_checkin`、次数自然不涨。
2. **徽标只认服务端状态**：前端以前完全按 `status` 上色，
   所以即使时间上早就该算违约，徽标也还是「待签到」——正文与徽标自相矛盾。

**已修（两处，互补）**：

| 改动 | 位置 | 作用 |
|---|---|---|
| **惰性结算** | `cloudfunctions/login` 新增 `settleMyViolations()` | 每次登录（含冷启动）顺手把**本人**已超时的预约判为违约、累加次数并按梯度下发禁约。**完全不依赖定时器** |
| **徽标按时间推导** | `pages/myReservations/myReservations.ts` 的 `displayStatus` | 待签到已过 `start+15min` → 徽标直接显示**「已违约」**＋危险色，不用等云端翻状态 |

**幂等保证**：惰性结算逐条用 `where({_id, status}).update()` 条件更新，
只有真正把 `pending_checkin`/`paused` 翻成 `no_show` 的那一次才计数；
即使和 `expireRecords` 撞在一起，也不会重复计数（新增用例守着）。

**口径一致性**：15 / 30 分钟以前在前端是**写死**的，现在统一从
`miniprogram/config/constants.ts` 读取，并有断言守着
「前端 == expireRecords == createReservation == login == roomList」五处同值。

**顺手统一的文案**：所有面向用户的「爽约」已改为**「违约」** ——
徽标「已违约」、我的页「违约 N 次」、后台「违约率」、禁约提示「因违约过多…」。
数据库字段（`no_show` / `no_show_count` / `violation_type`）**保持不变**，不影响历史数据。

**你要做的**：上传 `login` 云函数 + **重新编译**。

## 必读 I · 打烊前想约 2 小时被拒 / 页面没有结束时间可选（2026-09-16 修复）

**现象**：20:04 想约 `20:33 → 22:33`，弹出
「预约时间须在 08:00-22:00 开放时段内」，只能干等到明天。
而且选座页**只有开始时间和时长档位，没有结束时间**，超出就只剩失败。

**旧逻辑**：结束时间越过打烊 → **整段拒绝**。
**新逻辑**：**能约多久就算多久** —— 把结束时间**夹**到打烊时间。

### 新的时段规则（前端与云端逐条一致）

| 情况 | 处理 |
|---|---|
| 结束时间晚于打烊 | **截断到打烊**：20:33 约 2 小时 → 实际 `20:33-22:00`（1 小时 27 分） |
| 开始时间早于开门 | 前推到开门时间（**结束时间保持你选的那个**） |
| 开始时间已晚于打烊 | 无法截断 → 提示「请选择明天 08:00 之后再预约」 |
| 截断后不足 15 分钟 | 不放空号 → 顺延到次日开门时间，并明确告知 |
| 房间没配开放时段 | 一概不截断，原样通过 |

### 界面改动

- 选座页新增**「结束」时间选择器**，可以直接挑几点结束（时长档位退化为快捷方式）；
  手动选过之后时长档位显示「自定义时长」。
- **任何自动调整都会显式提示**（页面黄色提示条 + 下单抽屉里再提示一次），
  不会静默改你的时段；成功下单时若服务端又截断了一次，会弹窗告知实际时段。

### 三处实现必须同值

同一套规则被写在了三个地方，改一处必须同步另两处：

1. `miniprogram/utils/bookingWindow.ts`（前端显示 / 提交）
2. `cloudfunctions/createReservation/index.js`（下单放行）
3. `cloudfunctions/updateReservation/index.js`（改约放行）

已提供一致性核对脚本，**改完任一处请跑一次**：

```bash
node scripts/booking-window.parity.cjs
```

**你要做的**：上传 `createReservation` + `updateReservation` + **重新编译**。

## 〇、必读：一次性订阅授权机制（决定你能不能收到推送）

- 微信一次性订阅：**用户授权 1 次 = 只能下发 1 条该模板通知**，7 天内有效，用完即失效，需再次授权。
- 本项目的授权收集时机（已落地）：
  - **预约时**：弹窗一次性授权 **3 张** `[预约成功通知, 签到提醒, 客户预约提醒]`。
    - ①「预约成功通知」当场消费（预约即推）；
    - ②「签到提醒」、③「客户预约提醒」的额度被**预留**给后端定时器。
  - **取消时**：弹窗单独授权 **1 张** `[预约取消通知]`，当场消费。
- ⇒ **自测每个用例前，先确认对应模板的授权额度还在**（没弹过拒绝、且 7 天内）。
  - **普通的「拒绝」**（没勾授权卡底部那个「总是保持以上选择」）→ 重新做一次预约/取消动作即可**重新弹卡授权**。
  - ⚠️ **勾了「总是保持以上选择」再拒绝**（该勾选框**默认就是勾上的**）→ 微信把该模板永久记住拒绝，**再也不会弹卡**，重做动作也没用。
    此时只能按「**必读 A 第 5 条**」的两条路径恢复：① 用户自己去「… → 设置 → 订阅消息」手动打开；② 开发者换用一张新选用的模板（新 tmplId）。

## 用例 1 · 预约成功通知（① reservationConfirmed）

| 项 | 内容 |
|---|---|
| 触发 | 客户端预约创建成功 |
| 授权模板 | 预约时弹窗的 3 张之一（当场消费） |
| 操作 | 自习室列表 → 选座位 → 选时间段 → 确认预约 |

- [ ] 时间为「年月日 时分」24 小时制，且为**北京时间**
- [ ] 文案中的座位名（如「一楼 · A-1」）与所约座位一致

**失败排查**：
- 没收到 → 预约时授权弹窗点了「拒绝 / 取消」→ 再预约一次并点「允许」

## 用例 2 · 签到提醒（② checkinReminder）

| 项 | 内容 |
|---|---|
| 触发 | `expireRecords` 定时器（每 5 分钟扫描）发现「30 分钟内开始 + 未签到 + 未提醒过」的预约 |
| 授权模板 | 预约时弹窗的 3 张之一（**预留额度**，必须当时点了允许） |
| 操作 | **无需手动操作**。预约一个「30 分钟内开始」的时段，等待定时器自动触发（最多约 5 分钟） |
| 预期通知 | 收到「**签到提醒**」卡片 |
| 卡片字段（示例） | 签到地点：**静学馆 · A-1** ／ 签到时间：**2026年9月16日 14:50** ／ 温馨提示：**您预约的座位即将开始，请到店签到** |

- 实时日志里 `notify` 返回 `NO_OPENID`/`SEND_FAIL` → 历史预约缺 `payload.openid`（见下方「重要提醒」）

## 用例 3 · 超时 / 暂离预警（③ reservationWarn）

| 项 | 内容 |
|---|---|
| 触发 | `expireRecords` 把 `pending_checkin` 判为 `no_show`（开始 +15 分钟未签到）或 `paused` 暂离超 30 分钟 |

- [ ] 暂离超 30 分钟（用例变体）：`paused` 状态搁置 30 分钟以上 → 同样收到 ③，且释放座位

**失败排查**：

## 重要提醒（影响全部后端推送）

- **所有后端定时推送（②③）都依赖 `record.payload.openid`**，该字段在 `createReservation` 创建时落库。
- **升级前创建的旧预约记录没有 `payload.openid`** → 定时器推送会**静默跳过**（不影响主流程，也不报错）。
- ⇒ 自测②③**必须用升级后新建的预约**，不要用历史数据。

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| 授权卡**完全不弹** | ① 前端未重新编译 ② 下单入口走错 ③ 批量中某模板 ID 无效（全有或全无）④ 曾勾「总是保持以上选择」并拒绝 | 见「必读 A」「必读 F」；看 vConsole 的 `[订阅授权]` 日志 |

| 提示「你因违约次数过多，N 分钟后才能再次预约」 | 禁约期中（1 次 30 分钟 / 2 次 2 小时 / 3 次起 24 小时） | 后台「用户」→「解除禁约并清零」 |

| 选座页只有开始时间、选不了结束时间 | 旧版只有时长档位 | 见「必读 I」：已新增「结束」时间选择器 |
| 完全收不到某模板 | 当时授权被拒 / 过期 | 重新走一次对应动作（预约/取消）并点允许 |
| 报 `47003` | 某 `thing` 字段超 20 字 | `notify` 已做 `clamp(20)` 截断兜底，正常不会触发；若仍报，检查 `room_name`/`seatLabel` 是否异常长 |
| 报 `NO_TEMPLATE` | 模板 ID 与公众平台不一致 | 核对 `config/subscribe.ts` 4 个 ID |
| 报 `NO_OPENID` | 记录缺 `payload.openid`（旧数据）或定时器无 openid | 用新预约重测；确认 `createReservation` 已上传 |
| ②③ 定时器不推 | `expireRecords` 超时还是 3 秒 | 控制台改 20 秒；确认触发器 `0 */5 * * * * *` 存在 |
| ③ 字段错位 | 公众平台关键词编号非默认 | 改 `SUBSCRIBE_KEYS` 一行，不动业务代码 |
