# 签到模块优化方案（P2 之前执行）

> 状态：**待你拍板，尚未动代码**
> 调研来源：超星学习通（座位预约）、厦门大学嘉庚学院图书馆、天津师范大学图书馆、南昌大学图书馆、内蒙古民族幼儿师范高专图书馆、湖南人文科技学院图书馆、常州自习室连锁 SaaS 案例
> 现状基线：`pending_checkin → active ⇄ paused → completed / no_show`，已具备地理围栏 + 到店签到码 + 暂离

---

## 一、结论先行

你的系统**能力其实比想象中全**（有暂离、有围栏、有违约封禁），"畸形"不是缺功能，而是**三处结构拧巴**：

1. **一个动作给了两个并列按钮**（手动签到 / 扫码签到）；
2. **签退被叫成了"取消"**（active 状态下唯一的出口按钮是「结束使用」，语义是取消，缺失"履约成功"的正向闭环）；
3. **同类配置被拆成两张卡**（管理端「到店签到码」+「位置签到」）。

行业里这三处都有标准答案，改起来不伤数据模型。

---

## 二、现状诊断：六个"畸形"点

### 用户端

| # | 现象 | 为什么畸形 |
|---|---|---|
| U1 | 待签到卡片上并排 4 个等宽按钮：手动签到 / 扫码签到 / 改约 / 取消预约 | **一个"签到"动作占了两个主位**，且四个按钮视觉权重相同，用户不知道该点哪个 |
| U2 | 使用中卡片上是「暂离 / 续时 / 结束使用」 | 「结束使用」本质是**签退**，却走的是 `cancel` 语义（弹窗写"确定要提前结束这次使用吗"）。签退在行业里是**履约成功 +1**，现在是"取消"，正向反馈被吃掉了 |
| U3 | 暂离中只有「返回座位」按钮 | 行业要求返回必须**重新落座验证**（扫码 / 再判一次围栏）。现在是个纯按钮，等于"点一下就算回来了"，围栏白加 |
| U4 | 状态信息三层重复 | 状态徽标 + `countdown` 行 + `release-banner` 三条都在讲时间/状态，卡片又高又乱 |
| U5 | 首页没有待签到入口 | 之前诊断出你 `no_show_count=3` 的成因很可能就是"约了不知道去哪签"。现在得主动翻「我的预约」才知道要签到 |
| U6 | 三个签到入口各写一遍 | 我的预约页 / 预约成功页 / 扫码深链页都自行拼流程，规则散落 |

### 管理端

| # | 现象 | 为什么畸形 |
|---|---|---|
| A1 | 「到店签到码」和「位置签到（防拍照远程签到）」是**两张独立卡片** | 二者都是"签到方式配置"，商家要连着配两处、看两段说明。**这就是你要求的"不要重复出现相同功能的卡片"** |
| A2 | 预约列表还是 `.resv-item` 平铺行 + 4 个挤在一起的 mini 按钮 | 用户列表已经改成卡片了，预约列表没跟上；而且「结束 / 标记违约 / 取消并释放」三个破坏性操作平铺，容易误点「标记违约」 |
| A3 | 没有"现场视角" | 店长打开后台只能按列表翻，看不到"现在有几个人该到店没到、几个在暂离、几个快超时" |
| A4 | 违约只能标记，不能豁免 | 误判、用户申诉（"我明明在"）没有撤销入口。行业普遍允许管理员解除违约 |
| A5 | 没有占座治理手段 | 座位显示"使用中"但人不在——这是自习室运营最痛的问题，行业全靠**互督机制**解决 |

## 三、行业标杆对照

| 能力 | 行业通行做法 | 专注座现状 |
|---|---|---|
| 签到窗口 | 开始时间 **前后 ±20~30 分钟**弹性（嘉庚学院：开始后 30 分钟；学习通：前后 20 分钟） | ✅ 有（开始后 N 分钟，可配） |
| 签到入口 | **单一「签到」按钮**；扫码 / 定位是它的两种实现方式，不是两个按钮 | ❌ 手动、扫码并列 |
| 暂离 | 30 分钟；**用餐时段（11:00–13:00 / 17:00–19:00）放宽到 60~90 分钟**；返回需**扫码落座** | ⚠️ 有暂离，但无用餐放宽、返回无验证 |
| 签退 | 必须签退，**签退 = 履约成功 +1**；不退座记违约 | ❌ 叫「结束使用」，无履约正反馈 |
| 座位监督 | 任何人可扫码发起监督 → 被监督人 **20~30 分钟内落座或退座** → 超时记违约并释放座位 | ❌ **完全没有** |
| 违约 | 累计 3 次 → 停用 7 天；考试周 1 次即罚；学期末清零 | ✅ 有 |
| 防作弊 | 动态码（每 20 秒~1 分钟刷新）/ 位置围栏 / 手势 / 人脸 | ✅ 围栏（刚加）+ 每日动态码 |
| 管理端 | 实时看板 + 现场核销 + 申诉处理 | ⚠️ 只有列表 + 两张配置卡 |

> 关键洞察：行业把签到做成**一条完整的状态闭环**——`签到 → 暂离 → 落座 → 签退`，每个动作都有对应的"守约/违约"判定。你的系统缺的是中间的**"落座"**和最后的**"签退"语义**，以及外部的**监督**。

## 四、优化方案（三档，可单选可组合）

### A 档 · 结构纠偏（推荐先做，不动数据模型）

| 编号 | 内容 | 改动落点 |
|---|---|---|
| A1 | **合并签到入口**：只留一个主按钮「签到」，点击后由系统自动选路（有座位码→扫码；无→定位+围栏；围栏失败→手输店内码兜底）。原来的「手动签到 / 扫码签到」两个按钮消失 | `myReservations.wxml/ts` 的 `buildActionList`、`utils/checkin.ts` |
| A2 | **语义正名**：active 状态「结束使用」→「**签退**」；签退成功后记 **履约 +1** 并弹正向反馈（"已完成，连续履约 N 天"）。pending_checkin 下的「取消预约」保持不变（那才是真取消） | `myReservations.ts`、`checkin` 云函数（新增 `checkout` 语义分支） |
| A3 | **卡片主次分层**：每张卡只保留 1 个主行动按钮（实心）+ 1 个「更多」折叠（改约 / 取消 / 续时 / 评价）。按你的偏好——**不要一屏四个等宽按钮** | `myReservations.wxml/scss` |
| A4 | **管理端合并配置卡**：「到店签到码」+「位置签到」→ 一张「**签到方式**」卡，内部分区：① 位置围栏开关 ② 签到码开关 ③ 共用的房间选择器 | `admin.wxml/ts/scss`、`adminOps` 的 `roomGeo` + `checkinCodes` 合并为 `checkinConfig` |
| A5 | **管理端预约列表卡片化**：跟用户列表同款卡片（座位名 / 状态胶囊 / 用户 / 时间 / 操作区）；主操作与破坏性操作分层，「标记违约 / 取消并释放」收进二次确认 | `admin.wxml/scss/ts` |

**改动量**：中（5 个页面文件 + 1~2 个云函数小改）｜**风险**：低，不新增集合、不改状态机

---

### B 档 · 补齐行业标配（A 之后做）

| 编号 | 内容 | 改动落点 |
|---|---|---|
| B1 | **座位监督（互督）**：其他用户在座位图/扫码页对"使用中但无人"的座位发起监督 → 被监督人收到订阅消息，**20 分钟内落座或签退** → 超时自动记违约并释放座位。配套防滥用：同一座位冷却期、同一用户每日上限 | 新增 `supervise` 云函数 + `supervisions` 集合（或复用 `records`）、`expireRecords` 加扫描分支、用户端监督按钮 + 被监督提醒 |
| B2 | **落座验证**：暂离返回 / 被监督后返回，强制**重新走一次围栏判定**（或直接扫座位码）。堵住"人在店外点一下就算回来了" | `checkin` 云函数加 `return` 分支的围栏校验、`utils/checkin.ts` |
| B3 | **用餐时段暂离放宽**：11:00–13:00 / 17:00–19:00 发起的暂离，保留时长 30 → 90 分钟（可在管理端配） | `checkin` 云函数 + `adminOps` 配置项 + admin 页 |
| B4 | **违约豁免**：管理端可对单条违约记录「撤销违约」，同步回滚用户 `no_show_count` 与封禁 | `adminOps.userAction` 扩 `clear_penalty` 到记录级、admin 页 |

**改动量**：中大（新增 1 个云函数 + 1 个集合 + 订阅消息模板）｜**风险**：中，B1 要防恶意监督，B4 要防管理员滥用

---

### C 档 · 运营视角（可穿插）

| 编号 | 内容 | 改动落点 |
|---|---|---|
| C1 | **管理端「今日现场」看板**：四栏实时——待到店（含超时预警）/ 使用中 / 暂离中 / 今日已完成，点栏位直接跳对应筛选 | `adminOps.overview` 扩字段、admin 页新卡片 |
| C2 | **首页待签到常驻卡**：有临近/可签到的预约时，首页顶部出现一张小卡「A3 座位 · 距开始 12 分钟 · 去签到 ›」，直连签到流程。**这是根治"约了不知道去哪签 → 违约 → 封禁"的入口** | `home.wxml/ts` |
| C3 | **履约档案**：「我的」页把"连续签到 N 天"升级为"连续履约 N 天 + 累计自习时长"，签退才计履约，与 A2 联动 | `profile.ts`、用户档案字段 |

**改动量**：小~中｜**风险**：低

## 六、明确不做的事（避免过度设计）

- **不做人脸 / 手势签到**：成本高、微信端体验差，围栏 + 动态码已够，行业里图书馆也不用。
- **不做硬件门禁 / 灯控**：需要采购设备，属 P2 商业化范畴。
- **不引入新状态**：`paused`（暂离）已存在，B 档全部复用现有状态机，不新增 `supervised` 之类的状态（监督状态用 `payload` 字段承载，避免状态爆炸）。
