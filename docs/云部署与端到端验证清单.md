## 3. 数据库集合初始化 + 建立索引

> ✅ **只需建 3 个集合**：`users`、`records`、`categories`。
> ⚠️ **不需要 `rooms` 集合** —— 自习室/房间/座位信息实际存在 `categories` 集合（`type: 'room'`），代码里（云函数 + 前端）从未引用独立的 `rooms` 集合，不要建它。

### 3.1 创建集合 + 设置权限

云开发控制台 → 数据库 → 创建集合：`users`、`records`、`categories`。

**每个集合权限类型统一设为：「所有用户不可读写」**（最严格）。

> 📌 **前提**：本项目前端**全部**通过云函数（`wx.cloud.callFunction`）读写数据库，**没有任何 `wx.cloud.database()` 直连**（已 grep 全工程确认）。
> 因此集合权限对「小程序端直连」的限制，**不影响任何云函数读写**（云函数走服务端 SDK，天然绕过集合权限校验）。
> 设最严可**防外人用开发者工具直连你的库**，是安全最佳实践。

各集合读写归属核对（用于你确认权限是否可再放宽——一般不必）：

| 集合 | 云函数读 | 云函数写 | 建议权限 |
|---|---|---|---|
| `categories` | roomList / categoryList / aiRecommend | seedData（初始数据） | 所有用户不可读写 |
| `records` | adminStats / roomList / aiSummary | createReservation / checkin / leaveSeat / expireRecords / studyRecord / cancelReservation | 所有用户不可读写 |
| `users` | adminStats | login | 所有用户不可读写 |

> 若某天你决定让小程序端**直连**某集合（当前没有），再单独把该集合权限改成所需级别（如「所有用户可读 / 仅创建者可写」）。

### 3.2 建立索引

> 在控制台「数据库 → 某集合 → 索引管理 → 新建索引」，逐行按下表填。**每条索引的三要素**：索引名称（你自命名，建议带集合前缀方便识别）、索引属性（是否唯一）、索引字段（逐个字段添加 + 排序规则）。

#### A. `records` 集合（业务记录，索引最多）

| 索引名称 | 索引属性 | 索引字段（按添加顺序） | 服务哪类查询 | 是否必建 |
|---|---|---|---|---|
| `rec_type_created_at` | 非唯一 | `record_type`↑ + `created_at`↓ | 按类型+时间排序 | ⭐ 建议 |
| `rec_type_status` | 非唯一 | `record_type`↑ + `status`↑ | 类型+状态过滤（adminStats / roomList） | ✅ 强烈建议 |
| `rec_user_created` | 非唯一 | `user_id`↑ + `created_at`↓ | 「我的预约/学习记录」按用户倒序 | ✅ 强烈建议 |
| `rec_type_status_start` | 非唯一 | `record_type`↑ + `status`↑ + `start_at`↑ | expireRecords pending超时、roomList 区间占用 | ✅ 强烈建议 |
| `rec_type_status_end` | 非唯一 | `record_type`↑ + `status`↑ + `end_at`↑ | expireRecords active→completed | ✅ 强烈建议 |
| **`rec_type_status_updated`** | 非唯一 | `record_type`↑ + `status`↑ + `updated_at`↑ | **expireRecords 暂离超时回流（paused→active）** | ⚠️ 必建（见下） |
| `rec_user_type_status` | 非唯一 | `user_id`↑ + `record_type`↑ + `status`↑ | studyRecord 查某用户某类型某状态（如 findRunning） | ⚠️ 可选（用户名下记录多时建议） |
| `rec_room_seat_type_status_start` | 非唯一 | `room_id`↑ + `seat_id`↑ + `record_type`↑ + `status`↑ + `start_at`↑ | **createReservation 座位冲突检测**（同座位同时段不可重叠） | ✅ 强烈建议 |

> ⚠️ 上表最后一条 `record_type + status + updated_at` 对应 `expireRecords` 的 `paused` 暂离超时扫描，**数据量大时没它会查询超时/扫不全**，务必建。

#### B. `categories` 集合

| 索引名称 | 索引属性 | 索引字段 | 覆盖查询 | 是否必建 |
|---|---|---|---|---|
| `cat_type_code` | **唯一** | `type`↑ + `code`↑ | seedData 按 type+code 去重 upsert | ✅ |
| `cat_type_status_sort` | 非唯一 | `type`↑ + `status`↑ + `sort`↑ | roomList / categoryList 读列表排序 | ⚠️ 建议 |

#### C. `users` 集合

| 索引名 | 索引属性 | 索引字段 | 覆盖查询 | 是否必建 |
|---|---|---|---|---|
| `user_open_hash` | **唯一** | `open_id_hash`↑ | login 按 openid 查/幂等（防重复 openid 变体） | ✅ 强烈建议 |

#### D. 并发防重说明（当前项目用代码层校验，NULLABLE）

> ✅ **当前版本无需建防重索引**：`createReservation` 的冲突检测是**写入前**用 `where({ room_id, seat_id, status in [pending_checkin,active], 时间区间重叠 })` 查库实现的（应用层检查），**不依赖 `reservation_id` 字段**——本项目记录里**没有 `reservation_id` 这个字段**（用自动 `_id`）。
> 所以 DEPLOY §309 提到的 `{ reservation_id, status:'active' }` 唯一索引对当前代码**用不上，别建**，免得建一个字段全为空的索引。
> 若以后想在**数据库层**加双保险，需要先让 `createReservation` 显式写入一个 `reservation_id + status` 字段，再建 `(reservation_id, status)` 唯一索引 —— 这属于后续加固（见 PLAN-v3 backlog F7），非本轮必需。

> 💡 控制台填写的「唯一」含义：索引内字段值组合不允许重复。上面标 **唯一** 的，建立时下拉选「唯一」；其余选「非唯一」。
> ⚠️ **建完务必确认每条状态为「运行中/可用」**，不要停在「构建中」；否则查询不走索引。

> 索引命名规范参考：`<collection简写>_<字段>[_<字段>]`，如 `rec_type_status_updated`。控制台里所有索引在一个列表下，加前缀避免和其他集合混淆。

## 4. 配置 expireRecords 定时触发器

> `expireRecords` **默认不会自动跑**，必须建定时触发，否则暂离/超时/统计都不更新。
> ⚠️ 如果你在云函数页面**找不到「触发器」入口**（部分开发者工具/云开发面板版本不显示），直接用下面**方法 A**，绕开入口。

### 方法 A：`config.json` 声明 + 上传（✅ 推荐，文件已为你建好）

**本项目已内置** `cloudfunctions/expireRecords/config.json`：

```json
{
  "triggers": [
    { "name": "expireRecordsTimer", "type": "timer", "config": "0 0 * * * * *" }
  ]
}
```

> 📌 七字段 Cron：`0 0 * * * * *` = 每小时第 0 分第 0 秒触发（每天 24 次）。
> 之所以改为每小时：原本每天 03:00 一次会让「预约不到场」的座位整日显示被占、且爽约惩罚滞后；改为每小时后，逾期未签到会在 1 小时内释放座位并计入爽约。

操作只有一步：

1. 微信开发者工具 → 云函数 → `expireRecords` **右键 → 上传触发器**（配置已改为每小时）
2. 回到云函数页刷新，`expireRecords` 上应显示已挂 `expireRecordsTimer`

> 🔧 想更快验证：把 `config` 改成 `"0 */10 * * * * *"`（每 10 分钟）再上传；验证完改回 `"0 0 * * * * *"` 再上传一次。
> 📌 定时触发 **七个字段**（秒 分 时 日 月 周 年），别写成 5 字段。

### 方法 B：控制台手动建（若你能看到入口）

1. 云开发 → 云函数 → `expireRecords` →「触发器」→ 新建触发器
2. **定时触发** + Cron `0 0 * * * * *`（每小时）
3. 触发器列表应显示**运行中**

> 手动建时若 Cron 保存报格式错，多半是**五字段**写成了 `0 0 3 * *`；云开发要**七字段** `0 0 3 * * * *`。

### 验证触发

- 触发器列表应显示 **运行中**（方法 A 上传后刷新即可见）
- 手动冒烟（可选）：IDE → 云函数 → expireRecords → **测试**，入参 `{}`，期望 `success=true, data.{no_show,completed,auto_returned} ≥ 0`（前面是 counts）。

## 7. 遇到报错的速查

| 现象 | 检查 |
|---|---|
| 云函数调用报 `Collection not exists` | 集合未建/名未新建 |
| 查询慢/超时 | `records` 复合索引未建全（尤其 `status + updated_at`） |
| 签到后仍是 `pending_checkin` | `checkin` 是否已部署；签到窗口是否在允许区间 |
| 暂离不自动回流 | expireRecords 触发器未建 / Cron 未启用 |
| 部署报依赖缺失 | 云端未安装 `wx-server-sdk`，改「上传并部署：云端安装依赖」 |
| AI 无反应 | `aiClient` 需真实 key，无 key 应 fallback 文案（不报错） |
| 并发冲突 | 本项目用**应用层冲突检测**（无 `reservation_id` 字段，勿建该唯一索引）；排查 `rec_room_seat_type_status_start` 复合索引是否已建、是否「构建中」 |
| 「我的预约」白屏/报组件找不到 | `myReservations.json` 未注册 `loading-state/empty-state/error-state`（本次已修复）；改完后需**构建 npm → 清缓存 → 编译** |
| 改约失败 | `updateReservation` 云函数未上传；或新时段与现有预约冲突（返回 `SEAT_CONFLICT`） |
| 禁约仍被放行 | `createReservation` 未重新上传（含禁约校验）；`users.banned_until` 未写入（看 expireRecords 是否触发） |
