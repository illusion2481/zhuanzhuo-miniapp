## 0. 从报告看：真正该优化的是哪三层

按《系统功能与逻辑链路报告》§3 把 13 个功能模块扫一遍，`专注座`已经具备——

- ✅ 完整预约闭环（选座→下单→三方签到→暂离→超时违约→取消/改约）
- ✅ AI 选座 / 学习计划 / 番茄钟 / 学习排行 / AI 学习总结
- ✅ 管理后台（自绘趋势图、座位维护、信用管理）
- ✅ 订阅消息（4 模板）+ 工程质量（TS/入参白名单/268 项测试）

报告 §4 点出的**5 处跨端一致性风险**仍是最脆弱的点。

对照成熟产品（5 个已上线案例）共有的能力，`专注座` 的四块核心缺口是：

| 缺口 | 成熟产品做法 | 本系统现状 |
|---|---|---|
| 实时性 | WebSocket / 云开发 `watch` 实时推送（延迟 150–300ms） | 15s `setInterval` 轮询（见 `seats.ts:14`） |
| 留存 | 连续打卡天数 streak + 习惯日历 + 评分 | 仅单次签到 + 一次性 AI 总结 |
| 反馈/评价 | 座位/房间评分 + 标签，反向 feed 推荐 | 无（`feedback_tag` 只有管理端反馈标签） |
| 商业化（沙箱） | 充值/会员/卡券/支付 | 无（受主体资质约束，但仍可做沙箱演示） |

> 结论：优先把「实时性、留存、评价、埋点」这四块做成基础设施——这些不依赖企业资质、纯前端+云函数就能上线，ROI 最高。

## 2. 分优先级的功能优化清单（每条都带文件级落点）

### 🟥 P0 —— 体验地基（1–2 周，不依赖资质，先做）

#### P0-1 实时座位同步：用云开发 `watch` 替换 15s 轮询

- **现状**：`miniprogram/pages/seats/seats.ts:14` `POLL_INTERVAL=15000` 每 15s 定时拉占用，弱网/后台下"座位图绿却报已约"。
- **做法**：
  1. `seats.onLoad` 对 `records` 集合（按 `room_id + 日期` 过滤）建立 `db.collection('records').where({...}).watch()`
  2. `onHide` 关连接、`onShow` 重建（后台/锁屏连接自动断）
  3. 保留手动下拉刷新 + 轮询作为**兜底**（复用现有 `isRealtimeSeats()/describeRoomSource()` 提示逻辑）
  4. `expireRecords` 翻状态后 `watch` 自动推前端，无需再轮询
- **收益**：延迟 15s→300ms；同时减少约 9 成无效请求，降云函数调用成本。
- **风险**：watch 断连重建必做；测试重点：锁屏回前台后占用是否同步。

#### P0-2 rooms 页搜索 / 筛选 / 排序

- **现状**：`rooms.wxml` 只有楼层卡片网格，无搜索、无筛选、无排序；`seats.ts` 已有 `window/power/outlet/quiet` 特征高亮可复用 `matchFeatureFilter`。
- **对策**：rooms 页顶部加筛选条（靠窗/电源/静音/维护态）+ 关键词搜索（房间名）+ 按空闲率 / 距离打烊时长排序；筛选条件透传到 `seats` 页预筛。
- **复用**：`seats.ts` 的 `matchFeatureFilter`、`utils/bookingWindow.ts`（算距离打烊）。

#### P0-3 一键续时（替代改约）

- **现状**：只有 `updateReservation` 改约，需重选时段，麻烦。
- **对策**：`active` 状态记录结束前 15min 提醒 + 卡片"延长 30/60min"按钮，调用 `updateReservation` 重校验冲突（座位未被他人预约才放行）——完全复用现有开放时段"夹"逻辑（`bookingWindow.ts` + `createReservation`）。
- **注意**：改 `updateReservation` 的 SCHEMA（加 `extendMinutes`），但**别动** `CHECKIN_TIMEOUT_MINUTES/LEAVE_TIMEOUT_MINUTES/MIN_BOOKING_MINUTES` 四处口径（报告 §4 红线）。

#### P0-4 客服入口与反馈

- **现状**：`profile.wxml` 无客服入口；`admin` 无反馈处理。
- **对策**：
  1. `profile.wxml` 加 `<contact-button>` 客服会话；
  2. 已有 `feedback_tag` 分类（`CATEGORY_TYPE.FEEDBACK_TAG`），`adminStats`/`admin` 复用它做「我的反馈」列表 + 处理标记。

#### P0-5 埋点地基

- **现状**：仅排障日志（`utils/logger.ts` 只导出 `rlog`），无业务埋点。
- **对策**：用 `wx.reportAnalytics` 埋编译事件：`room_view / seat_tap / booking_confirm / checkin_done / study_start / share_send`；小程序后台配置自定义事件。
- **为什么先做**：没有埋点，后面所有增长动作都是黑盒。

### 🟩 P1 —— 留存与增长（2–4 周，基于 P0 数据）

#### P1-1 连续打卡 / streak + 学习习惯看板

- **现状**：`users` 只有 `no_show_count`/`banned_until`，无连续签到。
- **做法**：`users` 加 `streak` / `last_checkin_date`；checkin 云函数签到成功时递增/断签（跨天）重置；`profile` 或 `study` 页展示连续天数 + 周/月专注重趋势（复用 `studyRecord.summary` + `aiSummary` 的聚合）。
- **成熟参照**：打卡类产品「战绩海报 + 连续天数 + 称号」→ 连续打卡 3 天解锁 `打卡徽章`，AI 总结里顺带提到。

#### P1-2 评价评分（反向把 AI 选座做成飞轮）

- **现状**：无 `reviews`；`categories.feedback_tag` 只有管理端用。
- **做法**：
  1. 完成使用后（`status→completed` 时，或 `profile` 历史记录里）对座位/自习室打分（安静度/舒适度/电源可用）+ 标签（复用 `feedback_tag`）
  2. 新集合 `reviews`（`user_id/room_id/seat_id/score/tags/comment`）
  3. `aiRecommend` 在打分阶段把历史评分作为权重因子 —— **这是本系统 AI 差异化最大的一步**（成熟产品评价闭环正是推荐引擎的燃料）
- **UGC 安全**：评论走 `msgSecCheck`（现有 UGC 护栏已覆盖 `goal`，扩到 `reviews` 即可）。

#### P1-3 分享裂变（海报 + 邀请）

- **现状**：`utils/share.ts` 已有 `buildShare`（未接入口，报告 §5.4 列出为冗余）——直接复活它。
- **做法**：① 分享海报（canvas 生成带小程序码图片落云存储）② 邀请好友得"信用保护"（少计一次违约）③ 可选"拼座"（同行共约相邻座位）。
- **复用**：`utils/share.ts` 的 `buildTimeline`、现有 `openid` 体系。

---

### 🟦 P2 —— 商业化与合规（4–8 周，受主体资质约束）

#### P2-1 会员 / 次卡 / 优惠券 / 支付（沙箱先行）
- **约束**：个人主体**不能**接微信支付，必须企业主体 + 商户号。落地前必须让用户在微信公众平台确认。
- **沙箱做法**：`wallets` + `charge_records` 集合，演示充值/扣费（`MOCK_PAY=1`），前端只留 `wx.requestPayment` 骨架。
- **注意**：真实支付绝不写进代码（红线），只做演示态。

#### P2-2 多门店 / 发现页（仅当有连锁规划）
- `categories` 目前是单校区多房间模型。若要多门店，需先引入 `study_room` 门店维度 + 经纬度 + 地址，`rooms` 页加"附近"。

#### P2-3 异常监控 / 黑名单自动化
- 在现有违约梯度（30min/2h/24h）之上，`expireRecords` 增加"短时高频预约"识别，自动升级 `banned_until`，admin 数据看板加"异常 Tab"。

#### P2-4 分包加载
- 将 `seats`（含 `SeatMap`）拆为独立分包，进一步压主包（延续已做的 TDesign 裁剪成果），给商业化留体积空间。

## 3. 已有方案没提、但成熟项目验证过的三个增量

### 🔸 增量 A · 预约末端"评价闭环"（P1-2 已列，这里强调它联动推荐）
对完成后的预约弹评价浮层（评分 1–5 + 标签），数据回流 `aiRecommend` → 你在"效果"里能看见"系统推荐得越来越准"——这是产品可讲述的差异化故事，也是把 AI 能力从"演示"变成"资产"。

### 🔸 增量 B · 信用资产化（把违约系统从"惩罚"变成"激励"）
- 现有 `users.no_show_count / banned_until` 只有惩罚。成熟产品还做"信用分"：签到/按时归还 +分，违约 -分，信用分高 → 「优先推荐 / 免宽限」「分享海报带 ta 的名额保护」。
- 落点：`users.credit_score`，`login`/`checkin`/`expireRecords` 三处增减分，与 `no_show_count` 并存（不动现有违约逻辑，纯增量）。

### 🔸 增量 C · 数据合规与容灾（不点这个，后续所有加数据的功能都是雷）
- 埋点行为数据隐私告知：接入 `wx.reportAnalytics` 前，在*隐私协议*里说明收集哪些行为（预约/学习/评价）。
- `records` 复合索引（room_id, seat_id, status, start_at/end_at）若未建，P0 后规模上来前**必须**建（报告 §3.2 占用查询依赖它）。
- 云函数 `expireRecords` 已做分批（20/批），但**建议**加 `request_id` 记录本轮处理，便于回查。
- 定期导出（admin 看板加"导出 CSV"，复用 `seedData` 思路）。

## 4. 落地顺序与如何复用现有代码（逐步可验收）

| 阶段 | 关键交付 | 复用的现有资产 | 可独立验收 |
|---|---|---|---|
| **Sprint P0-1** | watch 替换轮询 | `isRealtimeSeats()` / `describeRoomSource()` / `expireRecords` | 座位状态变化 <300ms、后台→回前台同步 |
| **Sprint P0-2** | rooms 搜索/筛选/排序 | `matchFeatureFilter` / `bookingWindow` | 从浏览到预约 ≤15s |
| **Sprint P0-3** | 一键续时 | `updateReservation` / `bookingWindow.ts` | 可续期、冲突被拒 |
| **Sprint P0-4** | 客服 + 埋点 | `wx.cloud` 事件上报、`contact-button` | 后台可看漏斗 |
| **Sprint P1** | 连续打卡 + 评价 + 分享 | `checkin` / `users` / `utils/share.ts` | 3 天连打有徽章；评论回流 AI 推荐 |
| **Sprint P2** | 商业化沙箱 / 分包 / 黑名单 | `wallets` 新集合 / TDesign 裁剪成果 | 沙箱充值可核销、seat 分包上包成功 |

> ⚠️ 所有改动必须保持「报告 §4 的 5 处一致性」不动：`CHECKIN_TIMEOUT_MINUTES/LEAVE_TIMEOUT_MINUTES/MIN_BOOKING_MINUTES`、`config/subscribe.ts` 模板 ID、`createReservation` 事务返回值、开放时间"与"、座位特征命名。动完用 `npm run test:cloud`（268 项）+ `booking-window.parity.cjs`（15 项）回归。

## 5. 一句话方案

> 专注座是"功能扎实但缺运营心脏"的 MVP。**第一周**先上 `watch` 实时 + rooms 筛选 + 网上续时（用户一用就感知）；**第二三周**把评价做成 AI 选座的飞轮、把违约系统升级成信用分；**第四周起**在确认主体资质后上沙箱商业化与分包——成熟产品的路径一致，每步都复用了你已写好的工程资产（tests、aiRecommend、adminStats、utils/share.ts），不需要推倒重来。
